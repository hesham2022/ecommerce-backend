# Returns / RMA — Design Spec

**Sub-phase 10a** of the multi-vendor e-commerce roadmap. Buyer-initiated post-delivery returns, scoped per-item, with a vendor-driven approval state machine and a logical `REFUNDED` state that records refund obligations off-platform (real money movement comes when phase 9b adds Stripe refunds).

## Goals

- Buyers can request to return one or more items from a delivered sub-order, within the vendor's configured return window.
- Vendors can approve, reject, confirm receipt, and mark refunded — with a clean audit trail per transition.
- Inventory restock is a per-return decision the vendor makes at receipt.
- A sub-order's `fulfillmentStatus` flips to `RETURNED` automatically when all of its items have a CLOSED return covering their full ordered quantity.
- All flows reuse the existing hexagonal patterns (domain → abstract repo → relational entity + mapper + repo + module) and the existing audit infrastructure (`order_event` table extended with new `OrderEventType` values).

## Out of scope (deferred phases)

- **Stripe refunds** — phase 9b will plug `paymentsService.refundForReturn(...)` into the `REFUNDED` transition for CARD orders. This spec keeps the seam but doesn't implement the gateway side.
- **Carrier integration** — return shipping logistics are off-platform; only a free-text `returnTrackingNumber` is captured.
- **Vendor-initiated recalls** — only buyers can open returns in 10a.
- **Partial refunds** — refund amount equals the item subtotal (`unitPriceSnapshot × quantity`); "keep-and-discount" arrangements happen via chat.
- **Order-level cancellation** — pre-delivery cancellation is already handled by `SubOrderFulfillmentStatus.CANCELLED`. Returns only apply post-DELIVERED.

## Data model

Three new tables under the project's relational schema. All UUIDs are uuidv7-generated by the application layer (matches `OrderEntity.id` convention).

### `return_request`

| Column | Type | Constraints | Notes |
|---|---|---|---|
| `id` | uuid | PK | App-generated uuidv7 |
| `sub_order_id` | uuid | FK `sub_order.id` ON DELETE CASCADE | The sub-order being returned against |
| `buyer_id` | int | FK `user.id` ON DELETE RESTRICT | Denormalised for direct ownership query |
| `vendor_id` | uuid | FK `vendor.id` ON DELETE RESTRICT | Denormalised for vendor list query |
| `status` | enum `return_status_enum` | NOT NULL DEFAULT `'REQUESTED'` | See state machine below |
| `reason` | enum `return_reason_enum` | NOT NULL | One of: `NOT_AS_DESCRIBED`, `DAMAGED`, `WRONG_ITEM`, `ARRIVED_LATE`, `NO_LONGER_NEEDED`, `OTHER` |
| `reason_note` | text | NULL | Required when `reason = OTHER`, otherwise optional |
| `return_tracking_number` | varchar(255) | NULL | Set by buyer at SHIPPED_BACK |
| `total_refund_minor` | bigint | NOT NULL | Sum of `return_item.refund_amount_minor` |
| `restocked` | boolean | NULL | Set when transitioning to RECEIVED. NULL until then. |
| `reject_reason` | text | NULL | Set on REJECTED transition |
| `created_at` | timestamptz | NOT NULL DEFAULT `now()` | REQUESTED time |
| `decided_at` | timestamptz | NULL | First vendor decision (APPROVED or REJECTED-from-REQUESTED) |
| `shipped_back_at` | timestamptz | NULL | Buyer's ship-back confirmation time |
| `received_at` | timestamptz | NULL | Vendor's confirm-receipt time |
| `refunded_at` | timestamptz | NULL | REFUNDED transition time |
| `closed_at` | timestamptz | NULL | CLOSED transition time |
| `rejected_at` | timestamptz | NULL | REJECTED transition time (could be from REQUESTED or RECEIVED) |
| `updated_at` | timestamptz | NOT NULL DEFAULT `now()` | Auto-updated |

**Indices:**
- `idx_return_request_buyer_created_at` on `(buyer_id, created_at DESC)` — buyer's "my returns" list
- `idx_return_request_vendor_status` on `(vendor_id, status)` — vendor's filterable list
- `idx_return_request_sub_order` on `(sub_order_id)` — sub-order detail page

### `return_item`

| Column | Type | Constraints | Notes |
|---|---|---|---|
| `id` | uuid | PK | uuidv7 |
| `return_request_id` | uuid | FK `return_request.id` ON DELETE CASCADE | Parent RMA |
| `order_item_id` | uuid | FK `order_item.id` ON DELETE RESTRICT | The item being returned |
| `quantity` | int | NOT NULL CHECK (`quantity >= 1`) | How many units (≤ `order_item.quantity`) |
| `refund_amount_minor` | bigint | NOT NULL | Computed at create-time: `order_item.unit_price_snapshot × quantity` |
| `created_at` | timestamptz | NOT NULL DEFAULT `now()` | |

**Indices:**
- `idx_return_item_request` on `(return_request_id)`
- `idx_return_item_order_item` on `(order_item_id)`

**Defence-in-depth constraint** — partial unique index that prevents two open RMAs from claiming the same `order_item`:

```sql
CREATE UNIQUE INDEX uq_return_item_open_per_order_item
ON return_item (order_item_id)
WHERE return_request_id IN (
  SELECT id FROM return_request
  WHERE status NOT IN ('REJECTED', 'CLOSED')
);
```

This expresses "at most one non-terminal RMA per order_item." Because the predicate references another table, Postgres won't permit it as a true partial index — so we enforce it in app code via a `CHECK_OPEN_RMA_QUERY` in `returns.service.ts` inside a serializable transaction at create-time. The migration just creates the simple `idx_return_item_order_item` non-unique index for fast lookup; the uniqueness is application-enforced.

### `return_attachment`

| Column | Type | Constraints | Notes |
|---|---|---|---|
| `id` | uuid | PK | uuidv7 |
| `return_request_id` | uuid | FK `return_request.id` ON DELETE CASCADE | |
| `file_id` | uuid | FK `file.id` ON DELETE RESTRICT | Reuses existing `files` module |
| `created_at` | timestamptz | NOT NULL DEFAULT `now()` | |

**Constraint:** at most 5 attachments per RMA, enforced in app code at create-time.

### `OrderEventType` extension

The existing `order_event_type_enum` is extended with seven new values:

```
RETURN_REQUESTED
RETURN_APPROVED
RETURN_REJECTED
RETURN_SHIPPED_BACK
RETURN_RECEIVED
RETURN_REFUNDED
RETURN_CLOSED
```

Each event row references `subOrderId` (existing FK) and carries the `returnRequestId` plus transition-specific fields in `payload` jsonb (e.g., `restock: boolean` for `RETURN_RECEIVED`, `rejectReason` for `RETURN_REJECTED`). The sub-order's audit timeline at `GET /v1/orders/:id/suborders/:sid/events` (existing endpoint) shows fulfillment + return events interleaved chronologically without code changes — the controller already returns all event types.

## State machine

```
                                                    BUYER                         VENDOR
                                                  --------                       --------
                                                                              ┌─ RECEIVED ──refunded──▶ REFUNDED ──closed──▶ CLOSED
                                                                              │     │
                            ┌─ APPROVED ──ship-back──▶ SHIPPED_BACK ──confirm─┘     │ reject (item arrived damaged)
                            │     │                                                 ▼
       (POST)               │     │                                              REJECTED (terminal)
   buyer creates ──▶ REQUESTED    │
                            │     └─ reject (with reason)──▶ REJECTED (terminal)
                            │
                            └─ reject (with reason)──▶ REJECTED (terminal)
```

**Transitions table:**

| From | To | Actor | Endpoint | Required body |
|---|---|---|---|---|
| (none) | `REQUESTED` | buyer | `POST /v1/orders/:orderId/suborders/:subOrderId/returns` | `items[]`, `reason`, `reasonNote?`, `fileIds?` |
| `REQUESTED` | `APPROVED` | vendor | `PATCH /v1/vendor/returns/:id` | `{ status: 'APPROVED' }` |
| `REQUESTED` | `REJECTED` | vendor | `PATCH /v1/vendor/returns/:id` | `{ status: 'REJECTED', rejectReason }` |
| `APPROVED` | `SHIPPED_BACK` | buyer | `PATCH /v1/returns/:id/shipped-back` | `{ trackingNumber? }` |
| `SHIPPED_BACK` | `RECEIVED` | vendor | `PATCH /v1/vendor/returns/:id` | `{ status: 'RECEIVED', restock: boolean }` |
| `RECEIVED` | `REJECTED` | vendor | `PATCH /v1/vendor/returns/:id` | `{ status: 'REJECTED', rejectReason }` |
| `RECEIVED` | `REFUNDED` | vendor | `PATCH /v1/vendor/returns/:id` | `{ status: 'REFUNDED' }` |
| `REFUNDED` | `CLOSED` | vendor | `PATCH /v1/vendor/returns/:id` | `{ status: 'CLOSED' }` |

**Disallowed transitions** (return 422):
- Any forward skip (e.g., `REQUESTED` → `RECEIVED`)
- Any backward transition (e.g., `APPROVED` → `REQUESTED`)
- `CLOSED` or `REJECTED` are terminal — no further transitions
- Buyer attempting any vendor-only transition → 403
- Vendor attempting `SHIPPED_BACK` (buyer-only) → 403

## Endpoints

### Buyer

```
POST   /v1/orders/:orderId/suborders/:subOrderId/returns
GET    /v1/returns?subOrderId=&status=&page=&limit=
GET    /v1/returns/:id
PATCH  /v1/returns/:id/shipped-back
```

All JWT-guarded. Ownership: `return_request.buyer_id === req.user.id`. Cross-tenant access returns 404 (don't leak existence).

`POST` body shape:

```json
{
  "items": [
    { "orderItemId": "uuid", "quantity": 1 }
  ],
  "reason": "DAMAGED",
  "reasonNote": "Screen cracked on arrival.",
  "fileIds": ["file-uuid-1", "file-uuid-2"]
}
```

Response: `ReturnResponseDto` with full RMA shape.

### Vendor

```
GET    /v1/vendor/returns?status=&subOrderId=&page=&limit=
GET    /v1/vendor/returns/:id
PATCH  /v1/vendor/returns/:id
```

All JWT-guarded + vendor-role-guarded. Ownership: `return_request.vendor_id === <calling vendor>`. PATCH branches on body's `status` to dispatch the right transition. The single endpoint pattern matches the existing `vendor-suborders.controller.ts` style.

PATCH body shape:

```json
{ "status": "APPROVED" }
{ "status": "REJECTED", "rejectReason": "Item not eligible per our terms." }
{ "status": "RECEIVED", "restock": true }
{ "status": "REFUNDED" }
{ "status": "CLOSED" }
```

`restock` is only valid (and required) on the `RECEIVED` transition. `rejectReason` is required for `REJECTED`. The DTO uses class-validator's discriminated-union pattern.

### Admin

```
GET    /v1/admin/returns?status=&vendorId=&buyerId=&page=&limit=
GET    /v1/admin/returns/:id
```

Read-only moderation list. Admin cannot transition RMAs in 10a — disputes flow through chat / support.

## Cross-module integration

### Inventory

When the vendor transitions to `RECEIVED` with `restock: true`, the service calls the existing variant-stock adjustment path. The exact method name will be confirmed during implementation by reading `src/products/infrastructure/persistence/product-variant.abstract.repository.ts`. Implementation note: this MUST happen inside the same transaction that flips the RMA status, so a partial failure doesn't leave inventory and RMA out of sync.

### Audit events

Each transition emits one `OrderEventEntity` row with the appropriate new `OrderEventType` value. The event references `subOrderId` (FK) and carries `payload: { returnRequestId, ...transition-specific }`. This reuses the existing audit-events module — no new audit infrastructure.

### Sub-order auto-flip to `RETURNED`

When a transition lands on `CLOSED`, the service runs `tryFlipSubOrderToReturned(subOrderId)`:
1. Load all `order_item` rows for the sub-order with their `quantity`.
2. Load all `return_item` rows where `return_request.status = CLOSED` for those order_items, summed by `order_item_id`.
3. If for every order_item, `closedReturnedQty >= ordered.quantity`, flip `sub_order.fulfillmentStatus` to `RETURNED`. Otherwise leave it as `DELIVERED`.
4. The flip uses the existing `SubOrderFulfillmentStatus.RETURNED` terminal state — no state-machine changes needed.

### Refund (deferred to 9b for CARD orders)

The `REFUNDED` transition is logical-only in 10a. For CARD orders, phase 9b will add a `if (paymentMethod === CARD) { paymentsService.refundForReturn(...) }` block in `returns.service.ts` before the status flip. The spec marks this as a TODO comment but does not implement it.

## Error handling

All errors return `422 Unprocessable Entity` with structured `{ message, errors? }` payloads matching the project convention, except where noted:

| Condition | HTTP | Where |
|---|---|---|
| `now() > deliveredAt + vendor.returnWindowDays` | 422 | `POST` create |
| Sub-order not in `DELIVERED` status | 422 | `POST` create |
| `return_item.quantity > order_item.quantity` | 422 | `POST` create |
| Sum of open + already-closed-non-rejected return quantities for an order_item exceeds ordered qty | 422 | `POST` create |
| `reason = OTHER` without `reasonNote` | 422 | `POST` create |
| More than 5 file attachments | 422 | `POST` create |
| Invalid state transition (state machine reject) | 422 | All `PATCH` |
| Buyer attempts vendor PATCH or vice versa | 403 | All `PATCH` |
| Cross-buyer / cross-vendor access | 404 | All `GET` and `PATCH` |
| `restock` provided on non-RECEIVED transition | 422 | Vendor `PATCH` |
| `rejectReason` missing on REJECTED transition | 422 | Vendor `PATCH` |
| `RECEIVED` PATCH missing `restock` field | 422 | Vendor `PATCH` |
| Buyer attempts SHIPPED_BACK before APPROVED | 422 | Buyer `PATCH /shipped-back` |

## Testing strategy

### Unit tests

- **`return-state-machine.spec.ts`** — every valid transition (vendor + buyer), every disallowed transition (skip, backward, terminal-from-terminal). Both `canBuyerTransition` and `canVendorTransition` exhaustively covered.
- **`returns.service.spec.ts`** — uses an in-memory abstract repository (matching the `notifications.service.spec.ts` pattern):
  - Eligibility window enforcement (within / past)
  - Quantity validation (single item, mixed items, exceeding)
  - Open-RMA constraint (cannot open second RMA on same item while first is open)
  - Restock side-effect (true → stock incremented; false → unchanged)
  - Sub-order auto-flip when all items fully returned
  - Refund-amount calculation
  - Cross-buyer / cross-vendor rejection

### E2E tests

`test/returns/returns.e2e-spec.ts` runs against the existing Docker-orchestrated app via `request(APP_URL)`, mirroring `test/orders/orders.e2e-spec.ts`. Fixtures: vendor + product + variant + buyer + sub-order driven to DELIVERED status (reuse the buyer-confirms-delivery existing flow).

Test cases:
1. **Happy path full flow**: create → vendor approve → buyer ship-back → vendor RECEIVED+restock=true → REFUNDED → CLOSED. Assert sub-order `fulfillmentStatus = RETURNED`. Assert variant stock incremented.
2. **Partial happy path**: same, but only one of three ordered items returned. Assert sub-order stays `DELIVERED`.
3. **Window expired**: try `POST` after `deliveredAt + windowDays` → 422.
4. **Non-delivered sub-order**: try `POST` against an `AWAITING_CONFIRMATION` sub-order → 422.
5. **Reject from REQUESTED**: vendor rejects → terminal. Subsequent `PATCH` attempts → 422.
6. **Reject from RECEIVED**: vendor receives, then rejects → terminal. No refund. Stock not touched.
7. **Restock=false**: vendor RECEIVED with restock=false → variant stock unchanged.
8. **Duplicate RMA**: open RMA on item, try to open another on same item → 422.
9. **Wrong actor**: buyer PATCHes vendor endpoint → 403; vendor calls `/shipped-back` → 403.
10. **Cross-tenant**: another buyer tries to GET / PATCH → 404.
11. **Reason=OTHER without note**: 422.
12. **Reason=OTHER with note**: succeeds.
13. **6 attachments**: 422.
14. **Audit events**: after full flow, sub-order events endpoint shows 5 RMA events in order: REQUESTED, APPROVED, SHIPPED_BACK, RECEIVED, REFUNDED, CLOSED — interleaved correctly with the original DELIVERED_BY_BUYER event.

## Open follow-ups (deferred to phase 9b/10b/10c+)

- **CARD refund**: `if (paymentMethod === CARD)` branch in `REFUNDED` transition calling `paymentsService.refundForReturn(...)`. Phase 9b.
- **Auto-CLOSE after N days**: scheduled job to flip `REFUNDED` → `CLOSED` after 7 days of inactivity. Phase 10b.
- **Vendor-initiated recalls**: separate flow with admin moderation. Phase 10c.
- **Partial refunds**: vendor-set refund amount on REFUNDED. When 9b ships and vendors actually need flexibility.
- **Carrier integration for return labels**: when phase 11 brings carrier APIs into the platform.
